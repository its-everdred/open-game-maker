Product scope + architecture · design doc

Open GameMaker 2000

An adult signs in, talks or types a game idea, agrees a scope, and an AI build agent makes it in a sandbox from asset packs and code. They play it, edit it while builds run, branch it, and invite friends to play along.

As of 2026-10-26 Branch research Stage scoping, no tickets yet Prototype makeopen.games

The short version

Who V1 is for

Adults only (18+): Kevin's instance, his household's adults, and adults they invite. Teens come in V2; child accounts and parental controls in V3.

What makes it different

Voice-first creation, real asset packs instead of generated art, editing while the agent builds, versions you can branch and merge, and multiplayer from day one.

How it's built

TypeScript everywhere. React on Netlify, Node on Railway, hosted aiur running coding agents in E2B sandboxes, Colyseus rooms, a Railway bucket for assets.

What's safe by design

Untrusted game code never sees a secret. Games run on a separate domain. Only the commit service can write to GitHub. Paid packs never reach public repos.

Decisions waiting on you

Can friends outside the family be invited in V1?

Recommend: family only until the lawyer review, then open to friends. The plan already requires that review before anyone outside the family joins.

How much of branching ships in V1?

Recommend: a branch-aware data model plus basic screens (new version, switch, play either, voice-guided merge). Retrofitting branches later touches every subsystem.

Publish from any version, or only from main?

Recommend: only from main after a merge, so there's one published line.

How does the build allowance work?

Recommend: a daily allocation per member set by an admin, reset at local midnight, shown to creators as a friendly unit with a bar (never dollars).

What happens when the host leaves a multiplayer game?

Recommend: end the session with progress saved. Handing hosting to another player can come later.

Room size, split screen, and whether friends hear the build agent

Recommend: 4 players per room; split screen later; friends see "talking to the builder…" but don't hear it.

What happens to files in the Drive watch folder after import?

Recommend: leave them where they are and track what's done. Nothing of yours gets moved or deleted.

Two spends to approve when ready

Recommend: a small Railway Hobby spend to test multiplayer relay latency, and a priced sample before tagging the whole asset library with a vision model. No spending is approved yet.

Where will the tabletop maps come from?

Recommend: prefer free-use map makers and generator output; bought packs are fine as private inspiration. It decides which licenses intake sees.

Ten older questions in the release plan (§6)

Recommend: start with "kids playing in V1" (accept they can't yet) and "which child-only rules to keep for adults". See docs/spec/release-plan.md §6.

What building it taught us

  • Assets were hard, game code was easy. Mixed packs looked like two different games, and modular characters needed a bake step. Swapping to one Kenney pack fixed the look, the page weight (13 MB of models to under 1 MB) and the license problem at once.
  • Testing was the slowest part. Headless WebGL runs at 1–2 fps. A tick(seconds) hook that steps the game without rendering made the full loop testable on desktop and phone. It belongs in the SDK, and gm-verify builds on it.
  • Phones need their own care. Ogg audio, iOS's ringer switch and touch unlocks, safe areas, and Safari's bars each cost a fix. Assets need phone-sized variants.
  • Agents need metadata. Choosing darker music meant measuring tracks with ffmpeg; checking an animation meant reading model internals. Hence metadata cards.

Architecture

Three trust zones. The web app and backend hold secrets. Sandboxes and game pages run untrusted, agent-written code and hold none. The commit service is the only thing that can write to a creator's GitHub.

Making a game

  1. Creator talks it through: idea, style family, point of view, single or multiplayer.
  2. The voice agent checks the estimate against today's allowance and offers to trim, split or queue if it won't fit.
  3. The backend admits the job (slots, money reservation) and hands aiur a scoped ticket.
  4. The agent builds in a sandbox from the locked packs, choosing assets from metadata cards, and runs gm-verify.
  5. The commit service writes to the creator's repo; the build lands in the bucket and plays in the game iframe.

Editing while it builds

  1. Every editor change is a transaction {actor, rev, patches} on the current branch, against stable ids.
  2. Overrides apply on top of the latest build instantly, so editing never waits on the agent.
  3. Creator edits win over the build unless a job explicitly targeted that control.
  4. Publish pins the build and override snapshot, then folds overrides into design/*.json on that branch.

Playing with friends

  1. Owner taps Invite and shares a link. A friend signs in and lands in the room.
  2. While the owner edits, everyone receives the same design transaction stream and sees the same changes, plus the editor's cursor.
  3. Play ends the edit pause; everyone already has the build, so all start together.
  4. Each player reads only their own controls and camera; the owner's browser runs the simulation.

New assets arrive

  1. Kevin drops files in the Drive folder. The listener waits until uploads settle.
  2. Intake identifies the collection and checks its license first; unknown licenses wait in quarantine.
  3. It converts formats, makes phone and desktop variants, renders contact sheets and writes a metadata card per asset.
  4. Agents can use it immediately. It becomes a creation choice only if it completes a style family.

Branching and merging

  1. "Make a new version from here" creates a Git branch and a fork point in the design log. Nothing is copied.
  2. Each version builds and plays on its own; the game card shows them all.
  3. Merging combines code through Git (an agent resolves conflicts) and design state per id and field.
  4. The voice agent walks through only the real conflicts with side-by-side previews; the merge is previewed before it lands.

Release plan

What ships when

V1 MVP for adults

Voice creation, the editor, branching, first-class multiplayer, the asset pipeline with Drive intake and tagging, budgets and admin, sandboxed builds, releases, saves, forks. Adults only, admitted by the operator allow-list.

V2 Teens and polish

Teens as creators once vendor approvals arrive, split-screen and multi-editor multiplayer, gameplay rewind, drawing tools, image restyling, a CDN, paid generators if packs fall short, self-service credentials.

V3 Kids and families

Child accounts with guardian consent, one parental-controls module, self-hosted child voice, child repos, a parent help overlay, player voice chat, and possibly native packaging.

Rules that hold in every version

  • A general game maker, not a kids' product. Child rules live only in the V3 parental-controls module.
  • The engine is open source and ships no packs. Paid packs stay on Kevin's instance and out of public repos.
  • Sandboxed from day one. Untrusted code never sees secrets.
  • No spending without Kevin's explicit approval.
  • Tools need at least 1k GitHub stars unless an exception is approved.
  • Not legal advice. A lawyer reviews before any outside family joins.
